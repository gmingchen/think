# 众三思 · 数据库设计文档（MVP）

> 本文依据 `需求设计方案.md` 的业务规则做技术侧落地，聚焦表结构、字段与关系；页面/接口不在本文范围。
> 需求文档明确「不涉及数据库设计」，本文是其下游的技术产物。若与需求条款冲突，以业务规则为准并回改本文。

---

## 一、通用约定与技术假设

- **数据库**：MySQL 8.0，存储引擎 InnoDB，字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`。
- **主键**：全表统一 `id BIGINT UNSIGNED AUTO_INCREMENT`。
- **外键**：仅建立**逻辑外键 + 普通索引**，不使用物理 `FOREIGN KEY`（便于分库分表与数据订正）。
- **枚举字段**：用 `TINYINT` 存储，注释中标明取值含义；不使用 MySQL `ENUM`（改枚举需 DDL）。
- **表命名**：关联表（多对多中间表）用**双下划线**连接两表名，如 `decision__tag`；业务单表用单词下划线风格（如 `grp_member`）。
- **软删除**：`deleted` 逻辑删除；决策单删除时由**应用层**级联软删其评议、报告、复盘。
- **时间**：统一 `DATETIME`，由数据库或应用层维护时区；本层不存业务时区。

### 1.1 基础字段（所有表都包含，下文各表不再重复列出）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT UNSIGNED | 主键，自增（各表 COMMENT 按业务命名，如“用户ID”） |
| created_at | DATETIME | 创建时间（DDL：NOT NULL DEFAULT CURRENT_TIMESTAMP） |
| updated_at | DATETIME | 更新时间（DDL：NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP） |
| deleted_at | DATETIME | 删除时间（逻辑删除时写入，未删除为 NULL） |
| deleted | TINYINT | 是否删除（0-未删除 1-已删除） |

> 下文每张表的字段列表默认已含上述 5 个基础字段，仅列出该表的业务字段。

## 三、表结构详解

### 3.1 user（用户身份记录）

> 非独立注册账号，仅以微信 `openid` 记录身份，供发起人/评议人展示与复盘对照（对应需求 §3.1、§3.5）。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| openid | VARCHAR(64) | 否 | — | 微信 openid，唯一身份 |
| unionid | VARCHAR(64) | 是 | NULL | 微信 unionid（预留） |
| nickname | VARCHAR(50) | 否 | '' | 昵称 |
| avatar | VARCHAR(255) | 否 | '' | 头像（预设标识） |
| sex | TINYINT | 否 | 2 | 性别：0-女 1-男 2-未知 |
| inviter_id | BIGINT UNSIGNED | 是 | NULL | 邀请人 user.id（拉新溯源） |
| invite_count | INT | 否 | 0 | 邀请用户数（冗余计数） |
| status | TINYINT | 否 | 1 | 状态：0-禁用 1-启用 |

**索引**：`UNIQUE uk_openid (openid)`；`idx_inviter (inviter_id)`
**说明**：同一 openid 只一行，进入小程序即静默登录（`wx.login` 换 `openid`）自动建档；昵称/头像由用户主动填写（微信头像昵称填写能力）、填写时覆盖更新，`avatar` 存预设标识而非真实 URL。`inviter_id`/`invite_count` 为**群邀请拉新溯源**：受邀点开群邀请链接并完成登录建档的新用户，`inviter_id` 记为邀请人、邀请人 `invite_count` +1（与 §3.2 群组邀请同一链路，非独立功能）。基础字段（含 `deleted`）见 §1.1。

---

### 3.2 grp（群组）

> 用户自建、通过邀请链接他人加入（§3.1）。一张决策单只发布到一个群。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| name | VARCHAR(64) | 否 | — | 群名称 |
| avatar | VARCHAR(255) | 否 | '' | 群头像（预设标识，群主可修改） |
| user_id | BIGINT UNSIGNED | 否 | — | 群主 user.id |
| status | TINYINT | 否 | 1 | 1-正常 2-已解散 |

**索引**：`idx_user (user_id)`
**说明**：进群校验 = 判断 `grp_member` 是否已有该 user_id。**邀请码不落库**：邀请时由服务端结合 Redis 生成短时效 code（可设过期 / 一次性），随邀请链接/卡片下发，校验通过后写入 `grp_member`；本表不存 `invite_code` 字段。**群主可修改群名称/头像、可解散群**（`status`=2，解散时该群全部 `grp_member` 同步置 `deleted=1`、该群「评议中」的 `decision` 自动置 `status=4` 已关闭）、**可移除成员**（同退群：`grp_member.deleted=1`），成员可退出（`grp_member.deleted=1`）；退出/被移除/解散后成员关系失效，但已评议的评议人仍可回看其参与过的决策单（§3.1）。

---

### 3.3 grp_member（群成员）

> 记录「群—成员」的 openid 关系，是群内可见性的判定依据（§3.1）。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| grp_id | BIGINT UNSIGNED | 否 | — | 所属群 |
| user_id | BIGINT UNSIGNED | 否 | — | 成员 user.id |
| role | TINYINT | 否 | 2 | 1-群主 2-成员 |

**索引**：`UNIQUE uk_grp_user (grp_id, user_id)`；`idx_user (user_id)`
**说明**：点开邀请链接并完成登录建档者写入本表（成为成员）。加入时间即基础字段 `created_at`，不另设 `joined_at`。软删除保留唯一约束注意：退群用 `deleted=1`，重新入群若受唯一约束阻挡，应用层可复用原行 `deleted` 置 0（此时最近加入时间以 `updated_at` 为准）。**成员退群后，其已提交过评议的群内决策单仍可回看**（评议人都可见，§3.1）。

---

### 3.4 decision（决策单）

> 核心主表，贯穿需求 §3.4 生命周期：草稿 → 评议中 → 已截止 / 已关闭 → 已复盘；公开档的**审核闸门**内嵌在「草稿 ↔ 评议中」之间（详见 §四.10 状态机）。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| user_id | BIGINT UNSIGNED | 否 | — | 发起人 user.id |
| title | VARCHAR(120) | 否 | — | 决策单标题（一句话概括，≤30 字；列表与详情展示） |
| content | TEXT | 否 | — | 决策内容（发起人自由描述两难处境、背景与纠结点；不拆三思字段，三思为评议/AI/报告侧的分析框架） |
| options | JSON | 否 | — | 备选方案数组，发起人自定义、**≥2 项**（不限上限，应用层校验），每项如 `{"label":"..."}`；发布后锁定不可增删改（否则评议下标失配） |
| images | JSON | 是 | NULL | 决策单图片 URL 数组，**最多 3 张**（可选）；公开档随文本一并过 `mediaCheck`（§五.3）；发布后随 content 一并锁定 |
| visibility | TINYINT | 否 | 1 | 可见范围 1-仅自己(草稿) 2-群内 3-公开 |
| grp_id | BIGINT UNSIGNED | 是 | NULL | visibility=2 时的目标群 |
| cool_down_hours | INT UNSIGNED | 否 | 24 | 冷静期时长（小时），对应档位 12/24/72/168 |
| cool_down_end_at | DATETIME | 是 | NULL | 冷静期截止时间 = 发布时间 + 时长 |
| review_limit | INT UNSIGNED | 否 | 1 | 评议人数上限：**最少 1**；群内档 ≤ 当前群成员数、公开档 ≤ 100（§4.1）；有效评议数（实时统计）达上限后不再接收新评议 |
| status | TINYINT | 否 | 0 | 0-草稿（公开档含「审核中 / 审核不过退回」子态） 1-评议中（对外生效、接收评议） 2-已截止 3-已复盘 4-已关闭（发起人关闭评议，停止评议、不出报告）；公开档须 `check_status=2` 时才由 0→1 |
| check_status | TINYINT | 否 | 0 | 内容审核闸门（仅公开档 visibility=3 有意义）：0-无需审核 1-待审核 2-通过 3-不通过；≠２ 不进公开广场、不对他人可见；**=3 时发起人可就地改 content/options/图片/标签并重提**，重提自动回到 1 重审、不限次数（§五.3、§四.10） |
| ended_early | TINYINT | 否 | 0 | 未满冷静期标记 0-否 1-提前结束（§3.3、§3.5 对照） |
| report_generated | TINYINT | 否 | 0 | 报告是否已生成 0-否 1-是 |
| published_at | DATETIME | 是 | NULL | 发布时间（进入评议中时间） |

**索引**：`idx_user_status (user_id, status)`；`idx_grp (grp_id)`；`idx_visibility_status (visibility, status)`；`idx_cooldown_end (status, cool_down_end_at)`（供到期扫描生成报告/提醒）
**约束/校验（应用层）**：
- 必填项：title、content、options（≥2 个备选方案）、cool_down_hours、visibility、review_limit（§4.1）。思危/思退/思变不再是发起人字段，三思框架由评议/AI/报告承载。
- options 数组长度 **≥2**（最少两个、不限上限，发起人自定义）；决策单进入 `status=1` 后 options 锁定，不可增删改（以免评议 `option` 下标失配）；审核不过退回 `status=0` 期间仍可编辑，重提后重审。
- 群内决策单 `visibility=2` 时 `grp_id` 必填，且**发起人须是该群成员**（`grp_member` 中该用户未退群，不限于群主）；仅群成员可浏览/评议，**已评议的评议人退群后仍可回看**（§3.1）。
- **评议人数上限**：`review_limit` 最少 1；`visibility=2` 时 ≤ 当前群成员数、`visibility=3` 时 ≤ 100（§4.1）；实时统计的有效评议数达上限后**不再接收新评议**（已提交评议仍可修改）。
- **图片**：`images` 最多 3 张（JSON URL 数组，可空）；公开档随文本一并过 `mediaCheck`（§五.3）。
- **标签**：**仅公开档**（`visibility=3`）可选，每单最多 5 个（`decision__tag` 关联，§3.15）；标签发布后随决策单锁定。
- 有效评议数由 `review` 实时 `COUNT(*)` 统计（**不冗余计数**，§3.5）；截止时为 0 触发 AI 兜底报告（§3.6）。
- **审核闸门与状态机（仅公开档）**：`visibility=3` 提交后 `status=0` + `check_status=1`（审核期对外不可见、不进广场）；`msgSecCheck` 通过（有图片时 `mediaCheck` 一并审核）→ `check_status=2`、`status` 由 0→1（进广场、开始接收评议）；不通过 → `check_status=3`、`status` 保持 0，**允许发起人就地编辑 title/content/options/图片/标签并重提**，重提后 `check_status` 自动回到 1 重审（**不限次数**，风控交由审核接口 + 运营处置）。审核明细见 `decision_check`，本列只存当前闸门态（§五.3、§四.10）。
- **发布锁定（全档统一）**：无论哪一档，一旦 `status=1`（对外生效），`title`、`content`、`options`、`images` 与标签均**锁定**、不可编辑；要修改必须先「关闭评议」（`status`→4，停止评议、不出报告）后**重建新决策单**。防止评议基础漂移（§四.10）。

### 3.5 review（评议）

> 强制填写观点、一条有效、截止前可改（§3.1、§3.2）。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| decision_id | BIGINT UNSIGNED | 否 | — | 所属决策单 |
| user_id | BIGINT UNSIGNED | 否 | — | 评议人 user.id（≠ decision.user_id，禁自评） |
| `option` | INT UNSIGNED | 否 | 0 | 倾向的备选项在 decision.options 数组中的下标（0-based，应用层校验 < 数组长度）；⚠️ `option` 为 MySQL 保留字，SQL 中须始终加反引号 |
| content | VARCHAR(500) | 否 | — | 评议观点文字（不能为空，应用层校验） |
| check_status | TINYINT | 否 | 0 | 评议审核闸门（仅公开档 decision 下的评议有值）：0-无需 1-待审 2-通过 3-不通过；≠２ 不对外展示（§五.3） |

**索引**：`UNIQUE uk_decision_user (decision_id, user_id)`
**约束/校验（应用层）**：
- **禁自评**：`user_id != decision.user_id`（§3.1）。
- **一条有效**：同一 (decision_id, user_id) 仅一行，修改走 UPDATE 而非新增（§3.1）。
- **满员拒绝**：新增评议前（提交事务内）实时统计校验 `COUNT(review) < decision.review_limit`，满员不再接收新评议；已有评议在冷静期内仍可修改（§4.1）。
- **可改窗口**：`decision.status=1（评议中）` 时可改 `option`/content；`status` 变为 2（已截止）或 4（已关闭）后禁改（§3.1、§3.3）。**公开档**评议若 `check_status=3`（审核不过），评议人可在 `decision.status=1` 截止前**就地改内容**，改后 `review.check_status` 自动回到 1 重审（不限次数）。
- 决策单删除 → 级联软删本表（§3.1）。

### 3.6 report（决策报告）

> 冷静期截止或提前结束时生成（§3.3、§4.3）；零评议时为 AI 兜底（§3.6）。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| decision_id | BIGINT UNSIGNED | 否 | — | 对应决策单 |
| option_counts | JSON | 否 | — | 各备选项有效人数，如 `{"0":3,"1":5,"2":1}`（下标→计数，随 options 长度动态） |
| total_review | INT UNSIGNED | 否 | 0 | 有效评议总数 |
| is_ai_fallback | TINYINT | 否 | 0 | 1=零评议 AI 兜底生成（§3.6） |
| ai_content | TEXT | 是 | NULL | AI 三思参考正文（仅兜底时存，思危/思退/思变+权衡） |
| generated_at | DATETIME | 否 | — | 报告生成时间 |

**索引**：`UNIQUE uk_decision (decision_id)`
**说明**：各选项票数与「是否未满冷静期」在截止时快照，不受此后修改影响；「仅供参考」声明为固定文案，不落库（§五.2）。**报告仅发起人可见**；仅「到期截止 / 提前结束」（status=2）生成报告，「关闭评议」（status=4）不生成。

### 3.7 recap（决策复盘）

> 发起人回填结局，可选（§3.5）；一张决策单最多一条。

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| decision_id | BIGINT UNSIGNED | 否 | — | 对应决策单 |
| final_choice | INT | 否 | -1 | 最终选择：decision.options 下标（0-based）；-1=其他/未选 |
| actual_result | TEXT | 是 | NULL | 实际发生了什么 |
| reflected_at | DATETIME | 是 | NULL | 回填时间 |

**索引**：`UNIQUE uk_decision (decision_id)`
**说明**：回填后由应用层将 `decision.status` 置 3（已复盘）。复盘展示所需的「当初各评议人倾向与观点」实时关联 `review` 读取，**不冗余存快照**——截止后评议已锁定（不可改、不可单独删，仅随决策单整体删除），数据不会再变动，实时读取即可保证复盘不失真。

### 3.8 订阅消息（三表）

> 冷静期到期提醒发起人，采用微信**一次性订阅消息**（§3.3）：`subscribe_template` 配置模板 → `subscribe` 记录用户累计的授权额度 → `subscribe_log` 记录每次发送结果。基础字段见 §1.1。

#### 3.8.1 subscribe_template（订阅消息模板配置）

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| type | VARCHAR(30) | 否 | — | 通知类型：COOL_DOWN_END-冷静期到期提醒（当前仅此一类，预留扩展） |
| template_id | VARCHAR(50) | 否 | — | 微信订阅消息模板 ID |
| remark | VARCHAR(100) | 是 | NULL | 备注 |

**索引**：`UNIQUE uk_type (type)`

#### 3.8.2 subscribe（用户订阅额度记录）

| 字段 | 类型 | 允许空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| user_id | BIGINT UNSIGNED | 否 | — | 订阅用户 user.id |

## 四、关键约束与实现要点汇总

1. **一条有效评议**：`review` 唯一键 `(decision_id, user_id)`，修改即 UPDATE，不新增计数（§3.1）。
2. **禁止自评**：应用层校验 `review.user_id != decision.user_id`（§3.1）。
3. **评议内容查看校验**（§3.3）：查询评议内容的接口校验——**发起人**（`decision.user_id` = 当前用户，只看单条观点、不看票数汇总）**或已提交评议者**（已有 review 记录）才可查看；未参与评议者不可查看他人评议内容（含满员后未提交评议者）。非表结构约束，由接口层控制。
4. **可见性判定**：群内决策单访问前校验 `grp_member` 是否含当前 user_id；非成员拒绝，**例外**：在该决策单下已有 `review` 记录的评议人退群 / 群解散后仍可回看（§3.1）。
5. **截止/关闭锁定**：`decision.status` 由 1→2（已截止）或 1→4（已关闭）后，`review` 禁改、不再接收新评议；到期由定时任务扫描 `idx_cooldown_end` 触发报告生成 + 订阅消息发送（仅 `status=1` 参与扫描；关闭不出报告，§3.3）。**群解散时**该群 `status=1` 的决策单一并置 4（§3.2）。
6. **级联软删**：删除 `decision` → 软删 `review / report / recap / decision__tag`（§3.1）。**例外**：审核留痕 `decision_check / review_check`、举报 `abuse_report` 与审计日志 `operation_log` **不随级联删除**，保留供平台合规审计与事后追溯（§3.9、§3.10、§3.11、§3.13）。
7. **未满冷静期标记**：提前结束置 `ended_early=1`，复盘并列展示（§3.3、§3.5）。
8. **不做点赞、不做精选**：无点赞/投票/精选表，报告仅按各选项票数汇总（§4.3）。
9. **公开档审核闸门**：`visibility=3` 决策单及其评议以 `check_status` 控制对外可见（≠２ 不进广场/不展示）；审核明细分表存 `decision_check` / `review_check`（仅公开档写入）。群内/仅自己档 `check_status=0`，不审核（§五.3）。
10. **审核状态机与发布锁定**（对应需求 §3.4）：公开档决策单走「提交（status=0, check_status=1）→ 通过（status=1, check_status=2）/ 不过退回可编辑（status=0, check_status=3；编辑重提后 check_status=1，**不限次数**）」；公开档评议 `check_status=3` 同构允许评议人就地改后重审。**全档统一**：一旦 `status=1`，`title`、`content`、`options`、`images` 与标签均锁定；要改必须走「关闭评议（status=4，不出报告）→ 重建决策单」流程，避免评议基础漂移。
11. **操作审计**：举报处理、群解散、关闭评议、删除决策单等人工操作写 `operation_log`（§3.13），append-only、不随业务删除。
12. **评议人数上限**：有效评议数（实时统计）达 `review_limit` 后不再接收新评议；`review_limit` 最少 1，群内档 ≤ 群成员数、公开档 ≤ 100（§4.1）。
13. **公开广场查询**：广场列表 = 公开档且审核通过的 `decision`，按发布时间倒序，默认拉取最新 50 条、上拉分页加载更多；「随机查看」= 随机取一条 `status=1`（评议中）的公开单（应用层查询，无需新增表/索引字段）。
